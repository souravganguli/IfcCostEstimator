# Phase 1 Viewer Market Research

Research date: 2026-10-27
Status: Initial desk research complete; 13 capabilities are assigned to Phase 1A. Plan and plan-section drawings and a large-model performance benchmark (baseline and regression guard, no optimization) are assigned to Phase 1B. Other deferred candidates remain unassigned as described below.

## Purpose

Identify viewer workflows users may expect from tools they already know, then use the findings to prepare selectable, testable Phase 1A requirements. This is a product-feature benchmark, not a market-size study. It makes no claims about market share, adoption, or customer preference.

The benchmark focuses on 3D model viewing and inspection. Revit, AutoCAD, Arcol, cloud common-data-environment (CDE) products, and model-checking tools are included as context because users may encounter them, but their authoring, collaboration, clash, or estimating capabilities are not automatically viewer requirements.

## Product and Architecture Implications

- Familiarity should be evaluated at the workflow level: users expect to orient themselves, find model content, inspect it, and understand spatial relationships. The exact controls and required depth still need user selection and testable definitions.
- Selection, property inspection, hierarchy, search, measurement, and sectioning are plausible feature candidates, not commitments. Their feasibility depends on what the current IFC adapter can extract and what the renderer can support without exposing engine internals to features.
- Rule-based property coloring is a separate capability from generic display modes. Its specification should define single- and multi-property matching, rule precedence, behavior for missing values, color assignment, and how users clear or reset rules.
- The first-person minimap is separate from walkthrough movement controls. Define its compact side placement, model/level context, camera-position and heading indicators, and whether it is informational only or interactive.
- A 2D architectural plan view is more than a top-down camera angle. Define how IFC geometry and levels produce plan linework, including level selection, cut-plane height, visibility, and drawing conventions; assess these separately from 3D sectioning.
- Plan section lines and their corresponding 2D section views are a separate drawing workflow from 3D clipping. Define how a line is placed and oriented in plan, its view direction and extents/depth, how the section drawing is generated, and how users navigate between the marker and its view.
- CDE workflows commonly bundle the viewer with remote file management, accounts, comments, and sharing. This project is intentionally browser-only and local: no model upload, backend, external runtime service, model-data persistence, or telemetry. Similarity of UI must not silently import those services or assumptions.
- Authoring features in Revit, AutoCAD, and Arcol should not be treated as viewer parity. Editing, model creation, clash detection, cost estimating, and project collaboration require separate product decisions.
- Format counts and plan availability are vendor claims, not independently tested compatibility evidence. This application currently targets local IFC files; any format expansion needs its own licensing, parser, fixture, and acceptance review.

## That Open Feasibility Assessment

The current [That Open `engine_components` repository](https://github.com/ThatOpen/engine_components) is a useful implementation reference for the deferred drawing features:

- [`EdgeProjector`](https://github.com/ThatOpen/engine_components/blob/main/packages/core/src/fragments/EdgeProjector/index.ts) generates visible and hidden edge geometry in the browser from selected Fragments model items. Projection direction and near/far bounds can isolate plan, elevation, or section slices.
- [`TechnicalDrawing`](https://github.com/ThatOpen/engine_components/blob/main/packages/core/src/drawings/TechnicalDrawings/src/TechnicalDrawing.ts) turns projected geometry into 2D drawing linework, supports six standard projection axes, line layers, and multiple orthographic viewports. The [Drawing Editor example](https://github.com/ThatOpen/engine_components/blob/main/packages/front/src/drawings/DrawingEditor/example.ts) demonstrates projecting model edges into a plan drawing, editing annotations in paper space, and exporting DXF.
- The separate [`PlanMode`](https://github.com/ThatOpen/engine_components/blob/main/packages/core/src/core/OrthoPerspectiveCamera/src/plan-mode.ts) only constrains camera navigation; it is not a drawing generator.
- No built-in workflow was found for placing a plan section marker and maintaining its linked generated section view. That linkage and its UI would be application-specific.
- The packages are MIT-licensed; the inspected package metadata is version 3.6.0 and expects Three.js, web-ifc, camera-controls, and `@thatopen/fragments`. `EdgeProjector` consumes Fragments model IDs/local item IDs and obtains model geometry through Fragments APIs. Integrating it here would therefore require evaluating a supported bridge from the current local IFC loading path, same-origin worker/WASM delivery, Three.js compatibility, model identity mapping, and added bundle/runtime costs. No dependency adoption is approved by this assessment.

Conclusion: browser-side geometry projection is technically plausible, but That Open is not a drop-in implementation for this repository and does not solve linked section markers/views by itself. Both drawing features are assigned to Phase 1B, subject to a bounded prototype/fixture assessment; they do not block the 13 Phase 1A capabilities. The pre-run go/no-go below supersedes the earlier "explicit user go/no-go" expectation for unattended execution.

## Phase 1B Drawing Go/No-Go Recommendation (pre-run)

Performed as a desk and code assessment so the unattended run can start from an approved decision. Evidence:

- The app depends on `three@^0.186` and `web-ifc@0.0.78` directly; it does not use `@thatopen/fragments`. The IFC adapter ([src/adapters/ifc/index.ts](../../src/adapters/ifc/index.ts)) builds Three.js `BufferGeometry` from `StreamAllMeshes`/`GetGeometry`/`GetVertexArray`/`GetIndexArray`, keyed by model-scoped express ID. So triangulated geometry, per-element identity, and placement are already available in-app.
- That Open's `EdgeProjector`/`TechnicalDrawing` consume Fragments model/item IDs, not raw Three.js geometry. Adopting them would pull in `@thatopen/fragments` and a conversion/identity bridge from the current loader, with added bundle and runtime cost and version-alignment risk against the pinned `three`/`web-ifc`.
- Plan linework can instead be produced in-app by slicing the existing triangle meshes at the cut height (edges where triangles cross the storey cut plane), reusing the adapter's geometry and identity. This avoids a new dependency and keeps model-scoped identity intact. Section linework is the same technique on a vertical plane.
- No library provides the plan-marker-to-linked-section workflow; that is application code regardless of the projection choice.

Decision: **Go, without adopting That Open / Fragments (user-approved 2026-10-27).** Implement plan and plan-section linework from the existing in-app triangle geometry (mesh/cut-plane intersection) behind a new viewer drawing contract. Treat That Open as a reference only. The MIT pre-approval for a drawing dependency remains a fallback if the in-app approach fails the `1B_02` acceptance; a failure there is a non-blocking no-go that skips drawings and continues to 1C.

## Evidence Gaps and Follow-up Research

- Locate topical Autodesk Docs/ACC help pages for the model viewer's end-user controls, supported formats, measurement, sectioning, properties, and markup. The help landing page alone was insufficient evidence.
- Locate Revit and AutoCAD/AutoCAD Web documentation for the specific familiar navigation and model-inspection workflows to benchmark. Avoid treating desktop-only authoring commands as viewer requirements.
- For a future drawing tranche, compare Revit plan/section conventions with That Open's `EdgeProjector`/`TechnicalDrawing` pipeline and other viable browser IFC implementations. Prototype the IFC-to-Fragments/geometry bridge, storey and cut-height behavior, output fidelity, deployment assets, and section-marker-to-view linkage against representative local fixtures before proposing scope.
- Revisit Arcol's product documentation and Speckle Viewer using accessible pages or product documentation; current extraction failures are unknowns, not evidence of absent features.
- For Trimble Connect and BIMcollab, use help documentation or product demonstrations to validate detailed interaction behavior and separate plan/account requirements from core viewer workflows.
- Find direct product evidence for rule-based property coloring, including whether multiple conditions combine with AND/OR logic and how conflicting rules are resolved; keep these as open requirements questions until verified.
- Do not publish market-size, adoption, or user-preference claims without suitable independent sources or direct user research.
